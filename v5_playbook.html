How to actually build the plan

12 steps to a defended V5 mixture & curriculum.

The V5 Plan page explains what is being asked. This page is the recipe for doing it — each step in plain words, with the real datasets and token maths worked out, ending in the README you submit.

Running analogy: you are the head chef planning a season’s meal plan for an athlete (the model). Steps go: pick the events → choose drills → weigh your pantry → portion the plate → spot what you’re short on → grade ingredients → fix the daily vitamins → save dessert for race week → label easy/hard & quick/slow → write the weekly schedule → trial on a junior → restock the empty shelves.
1

Pick the exams you must pass

coach picks the meets
Before any percentages, list the benchmarks that define the model. That single list is the target — everything downstream is chosen to win these.
The data / the numbersCoding: SWE-bench, SWE-bench-Pro/Live · Agentic: Terminal-bench, τ-bench, BFCL, WebArena, GAIA · Reasoning/math: AIME, FrontierMath, LiveBench · General knowledge: MMLU · Indic: MILU + Indic evals.
✔ Done when: You have a written list of target benchmarks, grouped by capability lane.
2

For each exam, get the right textbook

match each meet to a drill
This is “compose backward”: every benchmark is matched to the dataset that teaches that skill. A lane is only real if a dataset fills it.
The data / the numbersSWE-bench → GitHub-issue+patch data · Terminal-bench → shell-session traces · BFCL/τ-bench → ToolBench/Bolt · AIME → math-reasoning traces · MMLU → general web (DCLM/FineWeb) · MILU → Sangraha/IndicCorp/Wikipedia.
✔ Done when: Every benchmark has at least one dataset mapped to it.
3

Take stock of your pantry

weigh the ingredients you own
Count what you actually have, in two numbers: samples (variety) and tokens (depth) — and treat published sizes as an upper bound, not trainable inventory (they drop after licensing, dedup, quality, decontamination and re-tokenizing with the V5 tokenizer). For chat/agent-style data, loss-masking trains the model on its own words, not user turns or tool logs, so a giant agent log is mostly not trainable — but plain pretraining is different: there every token is a next-token target.
The data / the numbersStack v2 ≈ 600M samples / ~900B tokens · ToolBench ≈ 120k samples / only ~80M tokens (tiny each) · DCLM/FineWeb ≈ trillions · Sangraha ≈ 251B · IndicCorp ≈ 20.9B · Wikipedia ≈ 10–90M per language.
✔ Done when: You have a table of samples + trainable tokens available for every lane.
4

Decide the plate — slice the budget into lanes

portion the meal
Fix the total budget (the course says 2.4–4T tokens; we’ll use 3T). Give each lane a % that sums to 100, then turn % into tokens so it’s concrete: tokens = share × budget.
The data / the numbersAt a 3T budget: Web 34% → ~1,020B · Code 25% → ~750B · Agentic 16% → ~480B · STEM 12% → ~360B · Reasoning 7% → ~210B · Indic 4% → ~120B · Long-context 2% → ~60B.
✔ Done when: You have a mixture table where the shares add to 100% and each is written in tokens.
5

Reality-check: pantry vs plate → find the STARVED lanes

do you have enough of each?
Put “tokens needed” next to “tokens available”. Where you need more than you have, the lane is starved — that’s the single most important output of this whole exercise, because it tells the cleaning pipeline what to go get.
The data / the numbersAgentic wants ~480B but only ~0.08B is trainable → massively starved. Reasoning wants ~210B, have ~30B → starved. Code wants ~750B, have ~900B → fine. See the table below.
✔ Done when: Every lane is marked ENOUGH or STARVED, with the shortfall in tokens.
6

Split the Indic dish into its four qualities

grade the ingredients
Don’t write one Indic number. Break the 120B into the four tiers by how much you can honestly source of each, and say when Sanskrit / Urdu / other languages enter.
The data / the numberse.g. Indic 120B → Verified (T0) 45% (54B, Wikipedia/textbooks — thin, so this caps you) · Unverified (T1) 35% (42B, Sangraha/IndicCorp) · Translated (T3) 12% (14B) · Synthetic (T2) 8% (10B, distilled).
✔ Done when: The Indic lane is written as four tier-numbers that add up, with a note on which languages and when.
7

Pin the non-negotiables (the floor) — because of OPUS

the vitamins you never skip
During training an auto-selector called OPUS keeps only data that helps the target benchmarks — but it peeks at just the first ~512 tokens and its benchmarks are English/coding-heavy, so it would throw away Indic and agentic. Set minimums it may never cross.
The data / the numbersAlways-on floor: agentic ≥ 8% · Indic ≥ 3% of the budget — with per-language token minimums inside the Indic lane (e.g. Hindi ≥ 20B, each low-resource language ≥ 2B), never a per-language % of the total (0.3% × 22 languages would blow past the whole Indic lane). Safety is a cross-cutting tag counted inside its host lanes, held ≥ 1%.
✔ Done when: You have explicit floor percentages the selector is forbidden to go below.
8

Save dessert for last — the anneal reserve

peak nutrition before the race
Hold back a slice of your very best data for the final cooldown (~last 2%, learning-rate→0), where what the model sees last sticks hardest. Spend it only then.
The data / the numbersReserve ~2% (~60B) that sits inside the 3T (core 2.94T + anneal 0.06T, not an extra 60B): premium verified Indic + PhD-grade LaTeX/math + the cleanest agentic traces. Those tokens still count toward their lane totals.
✔ Done when: A named reserve of best data with a % and a rule: “fed only in the cooldown.”
9

Sort by difficulty and thinking-length

label easy/hard and short/long
Add two more labels so the schedule can be deliberate: how hard each sample is, and how long the reasoning should be (the model is trained to obey low/medium/high/ultra tags). Long-context is separate: grow the sequence length in steps.
The data / the numbersDifficulty — Easy: “Capital of India?” · Hard: “Prove √2 irrational.” Depth — low ≤256 · medium ≤1k · high ≤4k · ultra ≤16k+ thinking tokens. Sequence length ladder: 4K → 8K → 16K → 32K.
✔ Done when: Every dataset is tagged with a difficulty band and (for reasoning) a depth band, with example boundaries.
10

Write the weekly schedule — the curriculum

plan the training weeks
The order matters as much as the mix. Broad web first (learn language + common sense), then code/STEM/reasoning, long-context late, premium anneal last. Bands must overlap (~15–20%) or the gradients spike. Show the mix as a few phase snapshots, not one static table.
The data / the numbersEarly (nursery): Web 55% / Code 15% / STEM 10% / Indic 8% / rest small. Mid: the 34/25/16/12/7/4/2 plate above. Anneal: tiny, premium-only. Blend 18% of the next phase into the current one.
✔ Done when: You have 3 phase-snapshot mixtures + a stated overlap rule between phases.
11

Trial on a junior first — proxy runs

test the plan on a trainee
Every number is a guess until tested cheaply. Commit to running competing recipes at 1B and 3B (V4’s small sizes) for a small budget, compare on the Step-1 benchmarks, and only promote winners. During the real run, OPUS gives ~8× token efficiency.
The data / the numberse.g. Recipe A (Indic 4%) vs B (Indic 6%) at 1B for ~20B tokens → if B lifts Indic evals without hurting English, promote to 3B → then 40B. OPUS keep-fraction ~50%.
✔ Done when: You have a written experiment plan: which recipes, which scale, which evals, promotion criteria.
12

Send the shopping list back to the kitchen

restock the starved shelves
Point the 8-stage cleaning pipeline at the lanes Step 5 marked starved — that’s the “cleaning continues, aimed at the starved slots” line. Then assemble everything into the README you submit.
The data / the numbersPriority queue for cleaning: agentic traces (biggest gap) → reasoning traces → long-context docs. README sections: target benchmarks · mixture (per phase) · Indic tiers · floor · anneal · bands · curriculum · validation plan.
✔ Done when: A prioritised cleaning queue + a complete, defended README ready to submit.
